# 화면 구조

토큰과 부품을 다 옮겨도 화면이 다르게 보이는 이유는 여기 있습니다.
**요소를 어떤 순서로, 어느 폭에, 어떤 층으로 놓는가**가 인상의 절반입니다.

이 문서의 내용은 실제로 화면을 띄워 촬영한 것에서 나왔습니다 (`preview/screens/`).
화면은 158개이고, 그것들이 **다섯 가지 아키타입**으로 수렴합니다.

---

## 1. 셸: 사이드바가 척추입니다

```
html · 100dvh · overflow hidden
└ flex
  ├ aside   240px 고정 (접으면 60px · 1024px 미만은 264px 드로어)
  │         background surface · border-right 1px · padding 22px 16px
  └ main    flex 1 · height 100% · overflowY auto
            padding 32px 40px          ← MAIN_PADDING (SSOT)
```

**스크롤하는 것은 `main` 이고 페이지가 아닙니다.** 사이드바는 화면에 고정됩니다.

가로 탭 바가 최상위 네비게이션인 앱과는 구조가 반대입니다.
이 시스템에서 가로 탭은 언제나 **2차 축**입니다 (한 화면 안의 단면 전환).

### 사이드바 안쪽 순서

```
Q 로고 글리프 (세로 스택) + 조직명
─────────────────────────────
홈
워크스페이스        ∨   ← 접이식 그룹
  RA               ●   ← 활성: 왼쪽 금색 세로선 + 배경 + 오른쪽 금색 점
    인허가 현황         ← 활성 그룹만 하위 메뉴 펼침
    보험 등재 조회
    …
연계 부서           ∧   ← 기본 접힘
업무                ∨
공통                ∨
설정                ∨
─────────────────────────────
MEDQRAFT CORE  v3.5.0    ← mono · muted · 버전 두 줄
Q-ATELIER      v1.3.0
THEME  ● DARK      ‹     ← 테마 토글 + 접기 버튼
아바타 사용자명
       MEMBER · ENTERPRISE
로그아웃
```

- 그룹 헤더는 mono · 작게 · muted (「자원 관리」·「모니터링·측정」·「추적성·문서」)
- 그룹 접힘 상태는 `qa-nav-grp-<키>` 로 각각 저장됩니다
- 사이드바 접힘은 **계정별 키**로 저장됩니다
- 모바일은 좌측 스와이프(임계 60px)로 닫힙니다
- 항목 여백 `11px 14px` · 아이콘 자리 24px · 활성 배경은 샴페인 10%

### 부서가 곧 네비게이션 구조입니다

메뉴가 기능별이 아니라 **역할별**로 묶입니다. R&D · RA · QA · 생산 넷이고
각 부서에 「허브」 화면이 하나씩 있습니다 (`/research` · `/ra` · `/qa` · `/m`).

내 부서는 「워크스페이스」에, 남의 부서는 「연계 부서」에 접힌 채로 놓입니다.
**같은 앱이 사람마다 다른 모양으로 열립니다.**

### 본문 우상단 고정 띠

```
● 엔터프라이즈 · CORE 0%        🔔③
```

구독 상태와 알림. 사이드바가 아니라 본문 위에 떠 있습니다.

## 2. 아키타입 다섯

### ① 허브 (부서 워크스페이스)

```
PageHd            금색 막대 · mono 영문 부제 · 큰 한글 제목 · 하단선
「이 페이지 사용법」 칩        ← PageGuide, 금색 테두리 pill
mono 라벨 「인허가 모듈」
모듈 그리드        auto-fill minmax(180px, 1fr) · gap 10
                  칸: 아이콘(샴페인 배경 사각) + 이름 · padding 14px 16px · minHeight 62
KPI 4열            라벨 + 큰 숫자 + 보조설명
가로 탭            「허가 준비 (2)」 「허가 후 변경 (1)」 · 부제 두 줄 · 활성만 금색 하단선
범위 안내 박스      ◆ 포함 / ◇ 제외 를 기호로 명시
엔티티 카드들       코드(mono) + 제목 + 배지 + 진행률 + 체크리스트 격자
```

허브는 **「이 부서 사람이 오늘 볼 것」의 목차**입니다. 데이터가 아니라 입구를 늘어놓습니다.

### ② 목록

```
<div>                                  ← 폭 제한 없음. 전체폭을 씁니다
  PageHd (제목 · 조항 부제 · 「새 X」 버튼)
  HelpNote                             ← 이 기능이 무엇인지 한 문단
  PageWidgetBoard
    · KPI 요약   (Grid minCol 140 · gap 12)
    · 목록       (EntityRow 반복 · locked)
    · ListPager
</div>
```

목록만 `LAYOUT` 폭 제한이 없습니다. 표와 행은 넓을수록 좋기 때문입니다.

### ③ 상세

```
<div maxWidth 820 · margin 0 auto>
  ← 목록으로                            ← 뒤로 링크가 맨 위
  PageHd (mono 상태 부제 「접수 · Major」 · 코드 제목 「CPL-2026-001」)
  주 액션 버튼                          ← 있으면 헤더 바로 아래
  StageTimeline                        ← 4~6칸 가로. 현재 단계만 금색 테두리
  SectionCard 여럿
    · 제목 + 부제
    · DetailRow 반복 (라벨 왼쪽 / 값 오른쪽 양끝 정렬)
    · 본문 문단
  「다음 단계」 카드                     ← 화면 끝에서 다음 행동을 제시
</div>
```

**제목이 이름이 아니라 «식별 코드»** 입니다. 이름은 부제로 갑니다.
규제 문서는 코드로 불리기 때문입니다.

마지막 「다음 단계」 카드가 이 시스템의 성격을 잘 보여줍니다.
브랜드가 「동반자」와 「놓침 0」이라, 화면이 끝나는 자리에서 **다음에 무엇을 할지 짚어 줍니다.**

### ④ 생성 폼

```
<div maxWidth 720 · margin 0 auto>
  PageHd (조항 부제 「ISO 13485 §8.2.1: …」 · 제목 · 오른쪽 「← 목록」)
  <Bx padding …>                       ← 폼 전체가 카드 하나 안에
    SegmentedChoice                    ← 큰 갈래는 라디오가 아니라 카드형 선택
    2열 필드 격자
    FormSection (구획이 필요하면)
    전체폭 필드 (요약 · 상세)
    체크박스 블록
    FormActions                        ← 상단 1px 경계 · 오른쪽 정렬
  </Bx>
</div>
```

**라벨 옆에 힌트가 같은 줄로 붙습니다.**

```
유입 채널  전화·이메일·포털·현장 등 자유 입력
성격 *     긍정 피드백도 §8.2.1 의 수집 대상입니다. 위험관리 가정을 검증하는 자료가 돼요.
```

라벨은 굵고, 힌트는 그 오른쪽에 muted 로 작게. 별도 줄로 내리지 않습니다.
필수 표시는 금색 별표입니다.

질문형 라벨(「어디서 온 정보인가요?」)과 조항 근거가 함께 오는 것은
「선생님」이라는 브랜드 정체성이 폼 구조로 나타난 것입니다.

### ⑤ 현장 모드 (`/m/*`)

**규칙이 통째로 다릅니다.** 장갑 낀 손이 태블릿을 쓴다는 전제입니다.

```
셸 폭       520px (폰) → 768px 이상에서 760px      ← .qa-field-screen
입력        키보드를 띄우지 않습니다
            수량은 숫자 패드 · 단위는 버튼 격자 (ea/set/box/kg/g/L/mL/m/roll)
선택        «채워진» 상태로 표시 (테두리가 아니라 금색 배경)
계산 결과    즉시 격자로 (로트 크기 · 코드 · 표본 n · Ac/Re) + 판정 배지
판정 근거    그 자리에 한 줄로 (d ≤ Ac(1) 합격 · d ≥ Re(2) 불합격)
저장        하단 고정 · 전체폭 · 초록 · 매우 큼
```

계약(`field-no-keyboard.test.ts`)이 이걸 강제합니다.
`<textarea>` 가 없어야 하고, `<input>` 은 누르거나 고르거나 스캔만 합니다.

## 3. 위젯 보드: 화면을 사용자가 재배치합니다

목록·허브 화면의 본문은 그냥 쌓인 것이 아니라 **보드**입니다.

```tsx
<PageWidgetBoard pageId="capa" pageGuideId="capa" userId={user.id} items={[
  { id: 'kpi',  title: 'KPI 요약',   node: kpiNode,  width: 'full' },
  { id: 'list', title: 'CAPA 목록', node: listNode, width: 'full', locked: true },
]} />
```

- 편집 모드를 켜면 **드래그로 순서 변경 + 표시/숨김**
- 위/아래 버튼도 함께 둡니다 (접근성·모바일)
- `locked: true` 인 항목은 **순서만 바뀌고 숨길 수 없습니다** (필수 UI 실종 방지)
- `board:<pageId>:<userId>` 로 localStorage 저장. 사용자별·화면별로 분리됩니다
- 평소엔 컨트롤이 안 보이고 편집 모드에서만 나옵니다

**`PageHd` 와 `PageGuide` 는 보드 밖에 둡니다.** 항상 고정 노출입니다.

> 이 구조가 쓸 만한 이유는, 「이 위젯을 보여줄까 말까」를 논쟁하지 않아도 되기 때문입니다.
> 다만 **잠금을 안 걸면 필수 UI 가 사라집니다.** 폼 본문·저장 바·주요 표는 반드시 `locked` 입니다.

## 4. 화면 안 요소 순서

다섯 아키타입에 공통으로 흐르는 순서가 있습니다.

```
1. 어디서 왔나        뒤로 링크 (상세만)
2. 무엇인가          PageHd: 막대 · 부제 · 제목 · 하단선
3. 이게 뭔지 설명     HelpNote / PageGuide 칩
4. 지금 상태         StageTimeline · KPI · 상태 배지
5. 내용             SectionCard · 목록 · 폼
6. 무엇을 할까       주 액션 · 「다음 단계」 카드 · FormActions
```

**설명이 3번에 온다**는 점이 특징입니다. 내용보다 먼저입니다.
규제를 처음 접하는 사람이 쓰는 시스템이라는 전제가 순서로 나타난 것입니다.

## 5. 폭을 고르는 법

| 화면 | 폭 | 왜 |
|---|---:|---|
| 목록 | 제한 없음 | 행과 표는 넓을수록 좋습니다 |
| 허브 | 제한 없음 | 모듈 격자가 화면을 채웁니다 |
| 상세 | **820** | 읽는 화면입니다. 넓으면 눈이 줄을 놓칩니다 |
| 생성 폼 | **720** | 입력은 좁아야 시선이 안 흩어집니다 |
| 현장 모드 | 520 → 760 | 폰과 패드 |
| 2단 (본문 + 사이드) | 1140 | |

`LAYOUT` 토큰에서 고르고, **폭을 잡았으면 `margin: 0 auto` 로 가운데** 놓습니다.
계약(`page-shell-contract.test.ts`)이 둘 다 검사합니다.

## 6. 옮겨 쓸 때

전부 흉내 낼 필요는 없습니다. 인상을 만드는 것은 이 넷입니다.

1. **왼쪽 사이드바 고정 + `main` 만 스크롤.** 가로 탭을 최상위로 쓰면 완전히 다른 앱이 됩니다
2. **`PageHd` 를 모든 화면에 같은 모양으로.** 금색 막대 · mono 부제 · 큰 제목 · 하단선
3. **읽는 화면은 820, 쓰는 화면은 720 으로 좁히고 가운데.** 전체폭으로 펼치면 인상이 무너집니다
4. **화면 끝에서 다음 행동을 제시.** 「다음 단계」 카드 하나가 시스템의 성격을 바꿉니다
